# CrabBoy Advance — Bug Fix & Enhancement Design Document

**Audience:** an AI coding agent implementing fixes against this repository.
**Subject:** `ssilkdev/CrabBoy-Advance`, a Rust GBA emulator (~15.8k LOC, reviewed at commit `a7c7717`).
**Prepared by:** automated multi-agent source review (5 parallel subsystem passes: CPU, PPU, APU, memory/peripherals, UI/app layer).

This document is self-contained: each fix has enough context (files, line anchors as of the reviewed commit, hardware-correct behavior, and an implementation sketch) to be picked up independently. Line numbers will drift as the codebase changes — re-locate by function/register name if they no longer match.

---

## 0. How to use this document

Work top-to-bottom by phase. Each phase is independently shippable and testable. Do **not** batch unrelated phases into one PR — several of these touch save-file formats or audio buffer layout and should be reviewable/revertable in isolation. Cargo tests already in `tests/emulator_tests.rs` are a reasonable regression baseline; add new tests colocated with each fix rather than only at the end.

Severity definitions used throughout:
- **Critical** — silent data loss, security/supply-chain exposure, a whole feature class producing no effect, or a crash reachable from untrusted input (ROM/save/controller/cheat data).
- **Major** — wrong output/behavior for a common case or well-known game mechanic; no crash, but visibly broken.
- **Minor** — edge case, rare code path, or accuracy gap unlikely to be hit by normal play.

## 1. Phase 0 — Security (do first, independent of everything else)

### 1.1 [CRITICAL] Auto-updater installs and executes an unverified binary
**Files:** `src/ui/updater.rs:166-287`, `src/ui/updater_dialog.rs:196-207`

`check_for_update` downloads `crabboy-advance.exe` from the GitHub release over HTTPS to the correct hardcoded repo (`REPO_OWNER`/`REPO_NAME` at `updater.rs:14-15` — that part is fine), but the **only** acceptance check before treating the file as trusted is `file_size > 100_000` (`updater.rs:203`). `restart_and_apply` (`updater.rs:251-287`) then renames the running exe aside and moves this unverified file into its place and executes it. Anyone who can get bytes into that GitHub release (compromised maintainer token, compromised Actions workflow, a malicious fork somehow substituted) gets arbitrary code execution on every user's machine on next restart. There is also a **TOCTOU window** (finding 1.2 below) between download completing and the user clicking "Restart & Apply."

**Fix — minimum bar (do this at least):**
1. Publish a `SHA256SUMS.txt` (or per-asset `.sha256`) file as part of each GitHub release, generated by the release script (`scripts/create_github_release.ps1` / `scripts/package_release.ps1`).
2. In `updater.rs`, after download, fetch the checksum file (same release, same HTTPS call pattern already used for the API), compute SHA-256 of the downloaded bytes (`sha2` crate), and reject if they don't match — before writing `.exe.new` to disk, or at minimum before `restart_and_apply` touches it.

**Fix — recommended (closes the compromised-release gap, not just corruption/MITM):**
3. Add Ed25519 signing: generate a keypair offline, embed the **public** key as a `const` in `updater.rs`, keep the private key outside CI (a maintainer signs each release asset locally, e.g. via a small `cosign`/`minisign`/`ed25519-dalek`-based script, and attaches `crabboy-advance.exe.sig` to the release). Verify the signature against the embedded public key before accepting the binary. This means even a compromised GitHub Actions token cannot produce a binary the updater will accept.
4. Re-verify (re-hash / re-check signature) immediately inside `restart_and_apply`, not only at download time, to close the TOCTOU window in 1.2.

**Fix — best (Windows-native):** Authenticode-sign the release exe and call `WinVerifyTrust` (or the `windows` crate equivalent) before executing the replacement. This is the standard Windows self-updater pattern and also satisfies SmartScreen/AV heuristics, but requires a code-signing certificate — treat as a stretch goal, not a blocker for 1-3 above.

### 1.2 [CRITICAL] TOCTOU between download and self-replace
**Files:** `updater.rs:166-218` (download), `updater.rs:251-287` (`restart_and_apply`)

The downloaded `.exe.new` can sit on disk for an arbitrary time (user reads the changelog, gets distracted) before `restart_and_apply` swaps it in, with no re-verification at swap time. Any local write access to that directory can substitute the file in that window.

**Fix:** covered by 1.1 step 4 — re-verify hash/signature immediately before the rename-and-exec, not only right after download.

### 1.3 [MAJOR] Updater shells out to `curl.exe` resolved via PATH
**Files:** `updater.rs:170,294`

Both the release-check and the binary download run `Command::new("curl.exe")`, resolved via `PATH` rather than an absolute path or a vendored HTTP client. A different `curl.exe` earlier on `PATH` runs silently instead, with proxy/cert/TLS behavior outside this app's control.

**Fix:** Replace with `reqwest` (rustls backend, no OpenSSL dependency headaches on Windows) or `ureq`. This also removes the external-process dependency entirely and makes 1.1's checksum/signature fetch simpler to implement in the same request path. If keeping curl for some reason, invoke it via `%SystemRoot%\System32\curl.exe` (absolute path) rather than bare `curl.exe`.

### 1.4 [MAJOR] Poisoned-mutex panic cascade in updater
**File:** `updater.rs` (13+ `status.lock().unwrap()` call sites, e.g. one polled every UI frame from `ui/mod.rs:778`)

If any updater background thread panics while holding the lock, the mutex poisons and every subsequent `.lock().unwrap()` — including the one on the UI thread's per-frame render path — panics too. Combined with `panic = "abort"` in `Cargo.toml`, this takes down the whole emulator over an updater-only fault.

**Fix:** Replace `.lock().unwrap()` with `.lock().unwrap_or_else(|poisoned| poisoned.into_inner())`, or switch to `parking_lot::Mutex` (no poisoning). Prefer the latter — it's a drop-in type swap.

## 2. Phase 1 — Critical correctness bugs

### 2.1 [CRITICAL] EEPROM save type is entirely unimplemented
**File:** `src/gba/mmu/cartridge.rs:78-128`

Grep for "eeprom" across `src/` returns zero hits. Games requiring EEPROM (Golden Sun, Mario Kart: Super Circuit, Fire Emblem series, many others) get writes silently dropped and reads returning ROM garbage — saves appear to work (no crash/error) but never persist. This is a silent-data-loss bug, which is worse than a crash.

**Fix — implementation sketch:**
- Add an `Eeprom` backend (new file `src/gba/mmu/eeprom.rs`) modeling the serial DMA protocol:
  - Storage: `Vec<u8>` of 512 bytes (4Kbit, 64×8-byte records) or 8192 bytes (64Kbit, 1024×8-byte records) depending on detected size (see 2.2).
  - Access is via DMA3 word-writes to the EEPROM-mapped address range. GBATEK reference: for ROM ≤ 16MB, EEPROM occupies `0x0DFFFF00-0x0DFFFFFF` region conceptually but in practice any access in `0x0D000000-0x0DFFFFFF`; for ROM > 16MB, only the top 256 bytes of the 32MB ROM space are EEPROM. Since the DMA transfers 16-bit values where only bit 0 is meaningful, implement a small state machine:
    - **Write sequence:** 2 start bits (`11`), then 6 bits (4Kbit) or 14 bits (64Kbit) of big-endian address, then 64 bits of big-endian data, then a stop bit (`0`).
    - **Read sequence:** 2 start bits (`11`), then address bits, then a stop bit (`0`); the *next* DMA read transfer returns 4 dummy bits then 64 bits of data MSB-first.
  - The state machine should live behind a `step_bit(bit: u8) -> Option<u8>` style interface driven from wherever DMA-to-cartridge writes land in `mmu/mod.rs`, mirroring how `rtc.rs`'s `step_gpio` already handles a similar bit-serial protocol — reuse that pattern for consistency.
- Wire persistence the same way `Flash`/SRAM already persist (check `save_manager.rs` for the existing save/load hook and extend it to cover the EEPROM backend).
- Add unit tests exercising a full write-then-read round trip for both 4Kbit and 64Kbit sizes.

### 2.2 [CRITICAL] No save-type detection — Flash(128KB) is hardcoded for every ROM
**File:** `src/gba/mmu/cartridge.rs:61-75` (`Cartridge::from_bytes_with_save`)

There is no scan for the standard ID strings. A `Flash` backend sized for 128KB Macronix is instantiated unconditionally. Plain-SRAM games happen to "work" only because they never issue Flash unlock sequences — this is luck, not correctness, and EEPROM games are actively broken by this (compounds with 2.1).

**Fix:** Scan the raw ROM bytes (the whole cartridge, not just the header) for these ASCII markers, in this priority order, and pick the backend accordingly:
```
"EEPROM_V"   -> Eeprom (size decided by later access-pattern heuristic, default 64Kbit; GBATEK notes real hardware/emulators generally default to 8KB/64Kbit unless proven 4Kbit by usage — flag as a follow-up tuning item, not a blocker)
"SRAM_V"     -> Sram (32KB)
"FLASH1M_V"  -> Flash (128KB, Macronix/Sanyo ID per 2.6)
"FLASH512_V" -> Flash (64KB)
"FLASH_V"    -> Flash (64KB, legacy marker predating the 512/1M split)
(none found) -> Sram (32KB) as the conservative fallback — matches historical emulator convention (mGBA/VBA-M do the same)
```
This is the same technique real emulators use (the strings are literally embedded in each game's linker data by Nintendo's SDK). Add this as a documented, testable function (`detect_save_type(rom: &[u8]) -> SaveType`) with unit tests using synthetic byte fixtures containing each marker.

### 2.3 [CRITICAL] Keypad IRQ (KEYCNT) is not implemented
**Files:** `src/gba/keypad.rs`, `src/gba/mod.rs:104-140` (`step_instruction` IRQ wiring)

`KEYCNT` is stored/returned as a raw register but bit 14 (IRQ enable), bit 15 (AND/OR condition vs. OR), and the comparison against `KEYINPUT` are never evaluated, and no `request_interrupt` call exists for it. Games/homebrew that rely on Keypad IRQ to wake from Halt/Stop ("press any key" low-power wait, used by several commercial titles) will hang indefinitely.

**Fix:**
- In `keypad.rs`, add a method `fn check_irq(&self, keyinput: u16, keycnt: u16) -> bool` implementing: if bit 14 clear, return false; else compare the bits of `keycnt & 0x3FF` against the *pressed* (inverted, since KEYINPUT is active-low) key bits — bit 15 set means AND (all selected keys must be pressed), bit 15 clear means OR (any selected key pressed).
- Call this from `gba/mod.rs::step_instruction` alongside the existing VBlank/HBlank/Timer/DMA/SIO IRQ checks, wired to fire on the same cadence keypad state is polled/updated (each time `KEYINPUT` changes, or once per frame at minimum).
- Add a regression test that sets KEYCNT for AND-mode on a specific button combo, asserts no IRQ with one button held, then asserts IRQ with all held.

### 2.4 [CRITICAL] PPU: HBlank flag/IRQ suppressed during VBlank scanlines
**File:** `src/gba/ppu/mod.rs:121-132`

The HBlank DISPSTAT flag and `irq_hblank`/`dma_hblank` triggers are gated behind `self.vcount < 160`. Real hardware sets HBlank on **all 228 scanlines**, including the 68 VBlank lines (160-227) — this underpins common "HBlank DMA during VBlank" tricks and any HBlank-IRQ-driven timing that doesn't stop just because the frame is in VBlank. Games using this will see stalled effects, missed audio mixer refills timed off HBlank, or corrupted per-scanline visual effects that also run during VBlank setup.

**Fix:** Remove the `vcount < 160` gate from the HBlank flag/IRQ/DMA-trigger logic; HBlank should assert on every scanline's horizontal blank period regardless of whether that scanline is also in the vertical blank region. Keep the *separate* VBlank flag/IRQ logic (which correctly should only assert for lines 160-227) untouched — these are two independent flags that happen to overlap in time, not mutually exclusive.

### 2.5 [CRITICAL] APU: Wave channel has no second bank — bank-switch technique broken
**File:** `src/gba/apu/dmg.rs:431-433, 548-554, 564, 582`

`wave_ram` is declared as a single `[u8; 16]` even though `bank`/`two_banks` fields exist and are presumably set from register writes. `read_wave_ram`/`write_wave_ram`/`sample()`/`step_timer` never consult `self.bank`. On real hardware there are two independent 16-byte banks; the standard trick is to write new waveform data into the *inactive* bank while the *active* bank plays, then flip the bank register to swap seamlessly. Here, "writing to the inactive bank" corrupts whatever is currently playing, and `two_banks` (64-sample extended playback) has no effect at all. Any Channel 3 usage relying on bank-swap (common in commercial GBA titles doing dynamic waveform synthesis) produces audibly wrong/glitchy audio.

**Fix:**
- Change storage to `wave_ram: [[u8; 16]; 2]`.
- `read_wave_ram`/`write_wave_ram` (the CPU-facing register access, active only while the channel is *not* the bank being played — check GBATEK for exact "read/write goes to the inactive bank while channel is on" semantics) must index by `!self.bank` (the bank *not* currently selected for playback) when the channel is active, and by `self.bank` when it's inactive/off — real hardware exposes only one bank's worth of address space (0x10-0x1F) at a time based on the `NR30` bank bit.
- `sample()`/`step_timer` must read from `self.bank` (the active bank), and when `two_banks` is set, treat the two banks as one continuous 32-sample (64-nibble) waveform rather than restarting at sample 0 within a single 16-byte bank.
- Add a test: write distinct patterns to each bank, flip the bank bit, assert playback reads the newly-selected bank's data.

### 2.6 [MAJOR] RTC command byte likely assembled with wrong bit order
**File:** `src/gba/mmu/rtc.rs:92-106, 147-156`

The Seiko S-3511A command byte (`0110 bbb r`) is transferred **MSB-first** on real hardware, unlike ordinary data bytes (LSB-first). `step_gpio` assembles the command identically to data bytes (`command |= bit << cmd_bits_received`, i.e. LSB-first). The magic-nibble check and `is_read` bit still happen to work by coincidence (the nibble `0110` is a palindrome and the r/w bit position is unaffected), but the 3-bit register selector (`cmd = (command >> 4) & 0x07`) comes out bit-reversed for any non-palindromic register number — e.g. register 4 (`RTC_CONTROL`) decodes as 1, register 3 (`RTC_FORCE_IRQ`) decodes as 6 (`RTC_TIME`). This breaks Pokémon Ruby/Sapphire/Emerald's boot-time RTC-control probe and any code touching `RTC_FORCE_IRQ`.

**Fix:** Assemble the command byte MSB-first: `command = (command << 1) | bit` (shift left and OR in the new bit at position 0) instead of the current LSB-first `command |= bit << cmd_bits_received`, while leaving the *data* byte assembly (separate code path) as LSB-first, matching GBATEK's documented protocol asymmetry. Verify against a known-good trace (e.g. cross-check register numbers 0-6 all round-trip correctly) before/after the change, and add a regression test per register number 0-6 confirming correct decode.

### 2.7 [MAJOR] Cheat engine does not implement real GameShark/Action Replay/CodeBreaker decryption
**File:** `src/gba/cheats.rs:39-99` (`parse_cheat_code`)

Real-world GBA cheat codes as distributed by every public GameShark/Action Replay v1-v3/CodeBreaker database are **encrypted** — a seed-table-driven XOR/add transform must run before the address/value pair is usable. This implementation treats every line as already-decoded plaintext hex `ADDRESS VALUE`, with prefix heuristics for CodeBreaker's `8`/`3` opcodes but no actual decryption. Every code a user pastes from a real cheat site will decode to garbage.

**Fix:** Implement the standard decryption seed tables per format (these are publicly documented, e.g. in VBA-M's/mGBA's cheat code source, or on GBATEK-adjacent community docs):
- **GameShark/Action Replay v1-v2 (GBA):** uses a fixed XOR/seed pass over each 8-byte code pair.
- **CodeBreaker:** uses a distinct seed table and a rolling-key transform applied per code line.
- Structure this as a `decrypt_gsa(code: (u32,u32)) -> (u32,u32)` / `decrypt_cb(code: (u32,u32), &mut CbState) -> (u32,u32)` pair of pure functions with unit tests against known plaintext/ciphertext pairs (several are published in old GBA emulator cheat-database source as test fixtures) so correctness doesn't depend on hand-verification.
- Keep the existing plaintext `ADDRESS VALUE` path as a distinct "raw" format option in the UI (useful for cheats a user derives themselves via the RAM searcher) rather than removing it.

## 4. Phase 3 — Minor bugs and code-quality issues

Grouped by subsystem; fix opportunistically or batch into a cleanup pass. None of these are user-visible in common play.

**CPU** (`src/gba/cpu/*`):
- `mod.rs:267` — condition code 15 (NV) treated as always-execute; should be always-skip.
- `arm.rs:49-106`, `thumb.rs:56-79` — empty LDM/STM register list doesn't special-case the documented "transfers R15, base ±0x40" quirk.
- `thumb.rs:43-53` — THUMB Format 16 with `cond==14` (reserved/undefined encoding) silently no-ops instead of raising the Undefined Instruction exception.
- `arm.rs:356` — register-shifted data-processing operand reads `Rm==PC` as `pc+8`; hardware gives `pc+12` for this specific addressing mode (extra internal cycle for register-controlled shift).
- `arm.rs:81,440` — `cpu.in_irq = false` clears on *any* SPSR→CPSR PC restore (LDM^, MOVS/ADDS PC), not only IRQ returns; verify against interrupt-dispatch logic for correctness under nested SWI/UND returns.

**PPU** (`src/gba/ppu/*`, `src/ui/screen.rs`):
- `blend.rs:59-118` — blending expands BGR555→RGB888, computes in 8-bit space, truncates back without rounding; causes occasional 1-step color drift vs. hardware's native 5-bit blend math.
- `screen.rs:412-464` — `apply_nvidia_adaptive_sharpening` is a dead, divergent duplicate of `apply_nvidia_adaptive_sharpening_image` (lines 347-408); delete it or route the raw-framebuffer path through the real implementation.
- `screen.rs:218-233,361` — per-frame `Vec` allocation/clone for the xBRZ RGBA conversion and the CAS sharpening pass; cache/reuse scratch buffers across frames instead of allocating fresh each call. Worth profiling at 6x scale + sharpening where this compounds.

**APU** (`src/gba/apu/*`):
- `mod.rs:236-245` — NR52 master-disable clears channel `active` flags but doesn't reset NR10-NR51 register contents, so re-enabling resumes with stale duty/envelope/frequency instead of hardware's zeroed state.
- `audio_output.rs:159-163,120-123` — the "3D Headphone Spatializer" applies crossfeed only; no actual interaural time-delay line exists despite the ITD delay buffer being present and used only for the unrelated 5.1 ambience path. Add a short angle-dependent delay to the crossfed signal to match the advertised feature.
- `audio_output.rs:198-199` — 5.1→stereo downmix uses center=0.6/surround=0.5, which isn't the actual ITU-R BS.775 coefficient set (−3dB ≈ 0.707, or the −6dB=0.5 variant, but not this specific pairing); fix the constants or stop citing the standard.
- `audio_output.rs:27,133,323-327,341-345` — the real-time CPAL audio callback and the emulation thread share a `std::sync::Mutex<VecDeque<f32>>`; the emulation thread can hold the lock across a large `drain`, risking callback stalls/underruns. Swap for a lock-free SPSC ring buffer (`rtrb` or `ringbuf` crate) so the real-time thread never blocks.
- Same buffer: on `lock()` failure the callback skips writing entirely (stale/looping audio) instead of zero-filling; and the overflow-drain at 6000 samples cuts ~3000 samples in one shot (audible click) rather than gradually trimming. Fix both alongside the ring-buffer swap.
- `mod.rs:469-479` vs `audio_output.rs:144,155-157,162-163` — master DMG/DirectSound mix uses a soft Padé limiter, but 5.1 center/LFE/surround channels hard-clamp; align on soft-limiting everywhere for consistent clipping behavior.

**Memory/Peripherals** (`src/gba/mmu/*`, `src/gba/dma/*`, `src/gba/timer/*`):
- `dma/mod.rs:88-145` — `DmaController::execute_channel` is dead code, never called (the live path is `Mmu::execute_dma_channel` in `mmu/mod.rs:501-602`), and has already diverged (missing FIFO special-casing, wrong `dad_ctrl` case-3 handling). Delete it to remove the maintenance hazard, or if there's a reason to keep two implementations, reconcile them.
- `gba/mod.rs:162-198` — DMA3 "Special" (Video Capture) start timing is never triggered; rare feature, low priority.
- `timer/mod.rs:55-74` — a single large `step(cycles)` call spanning ≥65536 prescaler ticks would under-count cascade overflows (only signals one overflow instead of N); unlikely given per-instruction stepping granularity, but worth a bounds check or a `while`-loop fix for robustness.
- `mmu/mod.rs:41,143` — `last_read` (open-bus emulation) is initialized to 0 and never written anywhere; unmapped-region reads always return 0 instead of last-fetched-opcode value. Low priority accuracy gap.
- `flash.rs:62-68` — Flash chip ID is hardcoded to Macronix 128KB regardless of the detected/configured save size; once 2.2's detection lands, also vary the ID bytes (and bank-switch command availability) by detected chip.
- `mmu/mod.rs:290-313` — `DMAxSAD`/`DMAxDAD` are write-only on real hardware but readable here; harmless in practice, flagged for completeness.
- `WAITCNT` is stored/returned but never consulted for access timing anywhere in `cpu` or `mmu` — ROM/SRAM access speed doesn't vary with configured wait states. Listed here as a timing-accuracy gap, not correctness-breaking for most games.

**UI/App** (`src/ui/*`, `src/gba/mmu/sio.rs`, `Cargo.toml`, `tests/`):
- `gif_recorder.rs:45-64` (called from `ui/mod.rs:353-357,689-693`) — GIF LZW encoding runs synchronously inside the `eframe::App::update` call, stalling the render/emulation loop when a recording stops. Move encoding to a background thread, mirroring the pattern already used for the updater's downloads.
- `updater.rs:439-446` — `test_fetch_latest_release_live` makes a real network call during `cargo test`, making CI/offline runs flaky. Mark `#[ignore]` and run in a separate opt-in CI job.
- `sio.rs:106-111,180-196` — loopback UDP multiplayer accepts any local `"SIO"`-prefixed packet with no handshake/shared-secret; low impact given `127.0.0.1`-only binding, but worth a simple session token if hardening is ever prioritized.
- `Cargo.toml:26` — `xbrz-rs = "0.1.0"` is a narrow-adoption, early-version crate; `winres = "0.1"` (build-dep) has an unmaintained upstream. Worth a `cargo audit`/RustSec pass and pinning/vendoring evaluation.
- `ui/mod.rs` is 1352 lines acting as a god-object for app state + all menu rendering. Not a bug, but a maintainability risk — consider splitting per-menu (File/Video/Audio/Tools) into submodules before adding more UI surface.

## 5. Suggested implementation order

1. **Phase 0 (1.1-1.4)** — security fixes are independent of the emulation core and should land first; they protect every user regardless of what else changes.
2. **2.1 + 2.2 together** (EEPROM + save-type detection) — these are the same feature; implementing detection without EEPROM support, or vice versa, leaves the bug half-fixed.
3. **2.3, 2.4, 2.5, 2.6** — independent of each other and of step 2; can be parallelized across different agents/PRs since they touch keypad.rs, ppu/mod.rs, apu/dmg.rs, and mmu/rtc.rs respectively with no file overlap.
4. **2.7** (cheat decryption) — independent, self-contained in `cheats.rs`.
5. **Phase 2 table** — tackle in any order; note 3.1 and 3.2 both touch CPU exception/mode-switching semantics and may be easier to reason about together even though they're separate bugs.
6. **Phase 3** — batch as a general cleanup pass, or fold individual items into whichever Phase 1/2 PR touches the same file (e.g. fix the CPU minor items alongside 3.1/3.2 in one CPU-focused PR).

## 6. Validation recommendations

- The existing `tests/emulator_tests.rs` (49 tests, confirmed to contain real assertions rather than placeholders) is a reasonable base — extend it with unit tests colocated per fix as noted in each section above, rather than only adding integration-level tests at the end.
- For PPU/APU hardware-accuracy fixes (2.4, 2.5, 2.6, and the Phase 2/3 PPU/APU items), cross-check behavior against publicly available GBA test ROMs where possible (e.g. timing/IRQ test suites and PPU/APU accuracy suites commonly used by other open-source GBA emulators) rather than relying solely on hand-written unit tests — these catch regressions unit tests won't think to cover.
- For the save-type/EEPROM work (2.1/2.2), test against at least one real commercial ROM header known to use each save type marker, using synthetic byte fixtures (do not commit copyrighted ROM data to the repo).
- For the updater security fix (1.1-1.4), add a test that constructs a tampered `.exe.new` and asserts `restart_and_apply` (or its verification step) refuses it.
